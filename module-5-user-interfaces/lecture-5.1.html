Three Mile Island, 1979: a UI failure

Imagine you're on shift. What could go wrong here?

  1. A relief valve stuck open and nuclear cooling water drained away. The controls showed neither the valve's position nor the coolant level.
  2. Many similar alarms and a confusing control layout made it hard to spot the problem.
  3. Operators didn't recognize the loss of coolant in time: their training hadn't prepared them, operating procedures didn't either.
  4. Partial meltdown and radiation leak: the most significant commercial nuclear accident in the U.S.

A critical design flaw: The UI said "safe" when the plant wasn't.

https://americanhistory.si.edu/tmi/04-03.htm and https://en.wikipedia.org/wiki/Three_Mile_Island_accident

Interaction design process

In Human-Computer Interactions (HCI),
you need to build up two types of fundamental knowledge:

  • "understand computers -- limitations, capacities, tools, platforms"

  • "understand people -- psychological, social aspects, human error"

Top quote: Dix, Finlay, Abowd & Beale, "Human Computer Interaction", 3rd edition, 2004

In domain-specific design, you must additionally understand:

  • context-specific factors -- connectivity in rural spaces, outdoor environmental use conditions

  • specific user groups -- not all people are the same, even within a subgroup (e.g, farmers, planners, policymakers)

  • users beyond people -- animals as technology users, non-human technology stakeholders (impacts to and from the environment)

  • devices beyond personal computers -- embedded and control systems

Dix, Finlay, Abowd & Beale, Human-Computer Interaction, 3rd ed., 2004, Figure 5.1

Prototypes, from low to high fidelity

  • Low fidelity: a paper prototype. Quick, cheap, easy to throw away.
  • Mid fidelity: a wireframe. Layout and structure, on screen, without the look.
  • High fidelity: a mockup or interactive prototype. Looks like the real thing.

Interaction Styles

Interaction styles support dialog between the computer and the user.

  • Command Line Interface (CLI)
    • e.g., terminal

  • Natural Language Interface (NLI)
    • e.g., chatbots

  • Graphical User Interface (GUI)
    • point and click
    • menus
    • drag and drop
    • WIMP: windows, icons, menus, and pointers!

pg 136, Dix, Finlay, Abowd & Beale, "Human Computer Interaction", 3rd edition, 2004

Command Line Interface (CLI)

Example: DayCent, a biogeochemical model used in agroecosystem simulation (e.g., nitrogen leaching, soil organic carbon, etc.)

  • CLI DESIGN CONSIDERATIONS: Linear program flow. How to manage decision logic? Provide user with options via arguments OR text-based menus. Good documentation is key!

DayCent example, https://www.nrel.colostate.edu/projects/daycent/

Natural Language Interface (NLI)

Example: Wolfram Alpha (more agriculture examples)

  • NLI DESIGN CONSIDERATIONS: Are there appropriate algorithms to parse user inputs? What is the breadth of possible inputs? Mode of user input: voice vs text. Good training data is key!

Wolfram Alpha example, https://www.wolframalpha.com/input/?i=what+is+the+total+acreage+of+farmland+in+the+US

Component-based design

Design and build each piece once, then reuse it everywhere.

Brad Frost: Atomic Design Ch2

  • Atoms: button, text input, badge
  • Molecules: search box (input and button), card
  • Organisms: navbar, form, table

  • Templates: Django templates

  • Pages: Django views.
    In Django, a view = one page: a URL route + a view function (maybe filled with data) + a template.

UI basics in practice...

Local structure: to support user goals within an application

  • knowing where you are -- color in the current page on the menu
  • knowing what you can do -- a menu of options
  • knowing where you are going, or what will happen -- on hover, explain where it goes
  • knowing where you have been, or what you've done -- a hyperlink turns purple once visited

Communicating how your design will achieve this?
Site map, color palette like a legend

Global structure: hierarchical organization and dialog

  • show what leads to what -- the menu has a hierarchy
  • show what happens when -- timer shows
  • include branches and loops -- repeating events
  • be more task oriented than a hierarchy

Communicating how your design will achieve this?
User journey map, connected mockups

Screen layout

  • Grouping and structure -- logical organization based on user understanding
  • Order of group and items -- follows the flow of user actions
  • Decoration -- used to denote meaning (e.g., font, color)
  • Alignment -- indicates flow of information (e.g., left to right reading)
  • White space -- used to separate, structure, and highlight

Communicating how your design will achieve this?
Site map, color palette like a legend

Listed principles from: Dix, Finlay, Abowd & Beale, Human-Computer Interaction, 3rd ed., 2004

Bootstrap

An open source collection of prebuilt, configurable, UI components and page layouts.
Think lego for web UI.

  • CSS + JavaScript: link two files from a CDN (a server that hosts the files). Nothing to install.
  • The most popular open-source front-end toolkit, started at Twitter in 2011
  • A 12-column grid, responsive to screen size
  • Dozens of components; customizable with CSS variables
  • Excellent documentation.
  • Good for rapid prototyping!

A pattern library and a component library to upgrade your web applications.

Bootstrap's grid = your grid

  • A page is rows of 12 columns.
  • A col-4 takes 4 of them: the same as a "4 col" piece in your kit.
  • Responsive: col-sm-6 col-lg-4 means 6 columns on a small screen, 4 on a large one.

Structure of a Django Application, with Bootstrap

flowchart LR
    accTitle: A Django application with Bootstrap
    accDescr: The browser sends a request to urls.py, which calls a view in views.py. The view reads data from models.py and renders a page template, which extends base.html. base.html links Bootstrap's CSS and JavaScript from a CDN and your style.css from static. The view returns the finished HTML to the browser, which loads Bootstrap and style.css to style it.
    B["Browser"] -->|request| U["urls.py"]
    U --> V["views.py"]
    V <--> M["models.py"]
    V --> T["page template
extends base.html"]
    T -->|HTML response| B
    CDN["Bootstrap CSS + JS
(CDN)"] -.-> B
    S["style.css
(static/)"] -.-> B

base.html links Bootstrap, then your style.css. Every page extends it, so Bootstrap reaches every page.

STEP 1: Journey map -> use case

User Journey Maps: what is the ideal user workflow?
Example: This is Service Design Doing: Mapping journeys

  1. Map the full flow: how someone uses your app, from start to finish.
  2. Circle one task: that's your use case. Who is the user, and what is their goal?
  3. Your 4 views are the pages this use case moves through.

This is the jumpoff point to begin laying out your app's pages!

STEP 3: Style for consistency

A blueprint shared across every page of your app.

Palette

  • Background (white is ok!), accent, font, and "highlight" colors
  • Generate one: Coolors or Adobe Color

Typography

  • 1-2 font families, at about 4 sizes: header, subheader, main text, small text
  • Google Fonts, or Bootstrap's defaults

Assets

  • Icons, images, videos: credit third-party content
  • Icons: Bootstrap Icons, Noun Project
  • Photos: Unsplash, Wikimedia Commons

Visual design for accessibility, digital.gov

Consider: web accessibility basics

  • Contrast: text at least 4.5:1 against its background. Check with the WebAIM contrast checker.

  • Color is never the only signal: pair it with a label or an icon.

  • Readable text: main text at least 16px, Bootstrap's default.

  • Alt text: every image says what it shows or does.

  • Components used as documented keep Bootstrap's built-in accessibility.
